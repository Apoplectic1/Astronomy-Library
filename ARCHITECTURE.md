# ARCHITECTURE.md

**Charter.** Subsystem mechanics — *how each module of the `Astronomy` library is built and works*. Organized **one section per buildable module** (plus the cross-cutting `Astronomy.Core` API conventions and the PCL native/interop/local-build story). Forward-looking design lives in `ROADMAP.md`; how to build/test/benchmark lives in `VERIFICATION.md`; the consumer-facing contract lives in `CONSUMERS.md`; domain rationale (science/unit conventions' *why*, algorithm provenance) routes through `DOMAIN.md`.

## Solution overview

`Astronomy.sln`: **x64 is the only fully-wired build config** (Debug/Release × x64). The solution also exposes AnyCPU/x86 entries, but they're unmaintained aliases — of the thirteen buildable `Astronomy.*` projects, nine map them to `Any CPU` and four newer ones (Core.Benchmarks, Contracts.Tests, Catalog.Tests — **not** Diagnostics, which maps to `Any CPU`) map them to x64. The eight vendored PCL projects map their x86 entries to `Win32`, which is dead weight: every vendored PCL vcxproj declares **only** `Debug|x64` / `Release|x64`, so those `Win32` mappings point at configurations that exist in no project file. Always build x64. It holds thirteen buildable projects, plus a `PCL` Solution Folder containing eight view-only PCL projects (`PCL.vcxproj`, the six 3rd-party `.lib`s — `cminpack`, `lcms`, `lz4`, `RFC6234`, `zlib`, `zstd` — and the `xisf.vcxproj` CLI utility) sourced from `Library\PCL\`. The PCL projects have `ActiveCfg` set but `Build.0` omitted **for the x64 solution configs specifically** (other configs carry Build.0, but x64 is the config that's built): full source visibility and IntelliSense / F12 in the IDE, but `Build Solution` and `msbuild Astronomy.sln` skip them. PCL rebuilds happen manually via `Library\PCL\src\pcl\windows\vc18\PCL.sln`.

### Architectural conventions

These are baked into the public API and must be respected when adding code:

- **Hemisphere convention.** `Latitude`, `Longitude`, and `Declination` are stored as **non-negative magnitudes**, with direction in companion bool flags (`Location.North` / `Location.West` / `Target.North`). Constructors normalize by **XOR, not override**: a negative magnitude is flipped positive *and* the companion flag is inverted, so `new Target(declination: -5.0, north: false)` stores `Declination = 5.0, North = true` — i.e. **+5° North**, not −5° South. (Sign "wins" only when the caller passed the positive-hemisphere flag; the two inputs compose rather than one taking precedence.) Internal math reconstructs signed values just before feeding geometry.
- **RA is decimal hours in `[0, 24)`**, not degrees. Declination is decimal degrees.
- **The `AltAz` / `TargetGeometry` altitude is unrefracted** — degrees above the mathematical horizon. This is a convention of the *geometric* primitives, not a library-wide guarantee: `Astrometry.Refraction.SaemundssonDeg` is public, and refracted altitude is a first-class output elsewhere (`Session.AltAzSample.AltDegApparent`, and the apparent-altitude paths in `AltitudeCurve`, `MoonEphemeris`, `SunPosition`, `SkyBrightness`). When adding a refraction term, be explicit about which of the two you are producing and coordinate across `AltAz`, `TargetGeometry`, `RiseSet`.
- **Azimuth** is degrees from North, clockwise, in `[0, 360)` — **half-open**. Due north is the seam: the `cosAz` clamp forces exactly `1.0` for a target north of the zenith, `Acos(1.0)` is exactly `0.0`, and the eastern-half flip computes `360.0 - 0.0`, so `AzimuthAtHourAngle` folds `>= 360.0` back to `0.0`. Nothing downstream renormalizes (`AltAz`'s ctor stores verbatim), so the fold has to happen at the source.
- **DateTime kinds — UTC is a hard contract, enforced centrally.** `Astronomy.Core.Time.JulianDate.FromUtc` is the single gate: every time-based primitive funnels through it (`SiderealTime.Local` routes there; normalizing callers arrive as `FromUtc(AsUtc(x))`), and it **throws `ArgumentException` on a non-`Utc` `Kind`** rather than reinterpreting. The reason is that `DateTime.ToOADate()` ignores `Kind` entirely and reads raw ticks, so a `Local`/`Unspecified` instant would be silently reinterpreted as UTC and return an answer wrong by the caller's UTC offset. Because the gate is central, no downstream primitive needs its own guard.
  - `TimeKindGuard.AsUtc(DateTime)` (internal) remains the **converting** sibling for entry points that accept a local-frame instant (`AstroUtil`, `MoonEphemeris`, `NightCalculator`, `Sun/*`): `Local`/`Unspecified` are treated as local and converted via the machine zone; `Utc` is a no-op. Converting entry points therefore still accept any `Kind`; everything else requires `Utc`.
  - `NightWindow` outputs are `Kind=Utc`. The recommended consumer-facing carrier is `Astronomy.Core.Time.ObservationMoment` (record struct, `(Utc, Zone)`) — build via `FromLocal(local, zone)` or `Now(zone)` and pass `.Utc` to math helpers.
  - `LunarAge.DaysAt` predates the central gate and throws on its own; it is now consistent with the gate rather than an exception to a lenient rule.
- **Immutability + `With(...)`.** `Location` and `Target` are immutable; mutations produce new instances via a `With` method that takes optional parameters.
- **D/M/S accessors are computed on read**, never stored. Don't add stored DMS fields — they would drift.
- **`Location` is the site, not the session.** Carries geography (lat/lon/elev/TZ), atmospheric (Bortle/ExtinctionK), and terrain (`LocalHorizon: IHorizonProfile`). It does NOT carry an observation moment, a target floor, or a minimum duration — those are per-session inputs that consumers thread explicitly. As of 2026-05-18 (Phase 2 of the Location refactor), the previously `[Obsolete]` `Horizon`/`Duration` scalars and the `DateTime` field have been removed entirely. Scheduling helpers (`BestSession.For` / `ResolveCandidates` / `SessionSolvers`, `NightCalculator.ComputeNight(location, utc)`, `AltAzCalculator.At(target, location, utc)`) take all per-session inputs as explicit parameters.

### Thread safety

`Astronomy.Core` is **thread-safe by construction** since the CoordinateSharp removal in commit `e602bdb`. Verified: zero mutable static fields, zero static caches / dictionaries / `Lazy<T>` / singletons; all public APIs take parameters with no hidden state. All inputs are immutable POCOs (`Target`, `Location`, `NightWindow`, `MoonAvoidanceProfile`); all returns are immutable POCOs, small structs (`AltAz`, `RiseSetResult` — note `RiseSet` itself is the static helper class, not the value type), or `IReadOnlyList<T>`. **Consumers may call any helper from any thread without external synchronization.**

Two caveats limit that promise:

1. **Caller-supplied delegates are the consumer's responsibility.** Methods that take `Func<...>` parameters — most notably `IntegratedQuality.OverSession(..., Func<double, double> altitudeQuality)` and `IntegratedQuality.HalvesAroundMidpoint(...)`, plus any future delegate-taking helper — invoke the delegate from whatever thread called the method. If a consumer passes a closure that mutates captured state (e.g. `int count = 0; alt => { count++; return ...; }`), thread safety of that closure is on the consumer. Pure / referentially transparent functions are always safe.

2. **`Astronomy.PCL` is NOT part of this contract.** PCL is a separate assembly (`Astronomy.PCL.csproj` + `Astronomy.PCL.Native.vcxproj`) wrapping the vendored PixInsight Class Library. `Astronomy.Core` never references it. The underlying PCL C++ library historically isn't safe to call across threads — assume single-threaded access until PCL's own concurrency story is documented per-API.

`NightCache` is a per-`Location` amortization helper: build once per caller planning pass, hand to multiple targets so each target's year work doesn't re-derive the same 365-day `NightWindow` series. The instance is immutable after construction; concurrent readers are safe. Several caches can be built in parallel for different locations.

### Code organization (high-level)

All ten folders, so the map matches the tree:

- `AltAz.cs` / `TargetGeometry.cs` — topocentric coordinate primitives (the core "where is this target right now" math).
- `Astrometry/` — the provenance core: `Meeus/` (the Meeus-backed algorithm implementations everything else rests on), plus `SiderealTime`'s consumers `ObserverInfo`, `AstroUtil`, `Refraction`, `RiseAndSetEvent`.
- `Time/` — `JulianDate` (the central UTC contract gate), `SiderealTime` (GMST/LST), `ObservationMoment`, `TimeKindGuard`.
- `Locations/`, `Targets/` — the immutable observer + target value types described above.
- `Horizons/` — `IHorizonProfile` and four implementations (`Scalar`, `Polyline`, `ObstructionTable`, `MaxOfHorizonProfile`) for flat-vs-azimuth-varying horizon math.
- `Night/` — twilight calculation, `NightWindow` (a single night's astronomical/nautical/civil dusk/dawn), `NightCache` (year-of-nights for one location).
- `Session/` — higher-level analysis built on the primitives: `AltitudeCurve` (uniform-grid sampling via linear LST advance — the speedup over per-sample `AltAzCalculator.At` comes from GMST being linear in UT, so the curve advances LST arithmetically instead of recomputing it; returns `IReadOnlyList<AltAzSample>` with `AltDegGeometric` + `AltDegApparent` + `AzDeg` per sample), `SessionAltitude`, `QualitySamples`, `AltAzSample`, `RiseSet`, `TransitTime`, `VisibilityWindows`, `CoarseVisibility`, `IntegratedQuality`, `BestSession`, `TargetOrdering`, `SessionSolvers`.
- `Sun/` — `SunPosition`, `SunEvents`, `SunPower`, `SunTracking`, `SunSeparation`, `SunHeliographic`.
- `Brightness/` — `SkyBrightness` (Krisciunas–Schaefer), `Bortle`, `Twilight`.
- `Moon/` — `MoonSeparation`, `LunarAge`, `MoonAvoidance`/`MoonAvoidanceProfile`; `MoonEphemeris.Sample(location, startUtc, step, count)` returns `IReadOnlyList<MoonSample>` with topocentric AltAz (geometric + apparent) + `DistanceKm` + `AgeDays` + `PhaseAngleDeg` + `IlluminatedFrac` per `step`. Pure-function per-night sampling primitive consumed by TargetPlanner's `MoonEphemerisEntry` cache axis; designed for the planned IntervalScheduler Plugin (ISP) cache shape.

## Astronomy.Catalog

- **`Astronomy.Catalog`** — `net10.0-windows`, `LangVersion latest`, `Nullable enable`, `ImplicitUsings enable`. The shared catalog-database library **and** the owner of the .xisf-library scanner. One `Catalog.db` (SQLite via `Microsoft.Data.Sqlite`) reconciles two sources onto **one canonical `target`**: the disk image library is **ACTUAL** (source of truth), N.I.N.A. Target Scheduler is the **PLAN**, and the catalog re-organizes the plan clean and anchored to actual. Each `target` carries both facets (disk identity + plan attributes) discriminated by `source_id` — `Actual` (on disk only), `Planned` (in TS only / not yet shot), `Both` (merged); `inventory_filter` (actuals per filter) and `exposure_plan` (goals) both hang off it. `Scan/` holds the moved `ImageLibraryScanner` + report types (depends on `Astronomy.XISF`). `Build/` holds the reconciliation: `TargetResolver` (pure, **coordinate-primary** — each TS target anchors to the nearest disk target within a tolerance, default 0.5° haversine (an *unaligned* mosaic-panel claim is limited to the tighter `PanelMatchToleranceDegrees`, default 0.1° — a name-aligned panel directory anchors at the full tolerance since the name confirms identity, while a merely-nearby unrelated framing stays unclaimed); name only validates; disk plate-solved coords win on merge; the TS guid is **retained on `Both` for write-back**; TS duplicates fold onto one canonical and name-mismatch / ambiguous / unanchored / out-of-range rows are reported in `CatalogBuildReport`, not dropped — and on the **write-back** side a multi-claimed cell is now *withheld* rather than merely reported: `WriteBackPlanner` holds it out of the auto-write plan as a `ManualGroup` carrying a structured `ManualReason` (`MultiPlan` / `DuplicateFold` / `IdentityConflict` / `NoMatchingPlan`) plus the competing `ManualPlan` rows for hand resolution, with `ReconcileNote` / `UnplannedFrames` for the no-plan case; consumers render that hold-back surface. The alias-fold escape that used to auto-write ex-alias multi-claims was removed 2026-07-23) and `CatalogBuilder.BuildAsync` (full rebuild: scan disk + read TS → resolve → `WriteCatalog` in one transaction; either source may be omitted). `Schema/` holds the POCOs/mappers + `schema.sql`; `SchemaManager` applies it idempotently — **no migration framework**: the catalog is fully derived (scan + TS import) and rebuildable, so a schema change just means deleting `Catalog.db`. **Harden rule:** never pass a raw TS integer into a CHECK/FK column — `TargetResolver` coerces unknown epoch/state/priority codes to a safe default and normalizes/clamps planned RA/Dec, so a single bad external TS row can't abort the rebuild. `CatalogStore` is the read/write surface (`WriteCatalog(graph)` replaces the whole catalog transactionally; `GetShotTargets()` = source `Actual`|`Both` **and `parent_target_id IS NULL`** is XFM's actual-only view — a `Both` target has frames on disk, so it belongs; planned-only is excluded, and so is every mosaic *panel* child even when it has frames, since the query returns only the parent grouping node — descend with `GetChildTargets(parentId)`. **A mosaic is modelled as a parent target plus one child target per panel** (`target.parent_target_id`, indexed `ix_target_parent`); that hierarchy is what per-panel write-back and panel-radius gating operate on); `TargetScheduler/TargetSchedulerReader` reads TS's `schedulerdb.sqlite` read-only (Mode=ReadOnly + busy-timeout, explicit columns); `TargetScheduler/TargetSchedulerWriter` (+ pure `WriteBackPlanner` / `SingleTargetPlanner`) writes reconciled disk counts back into a **local** TS copy (Phase 4 engine — bulk or surgical single-target, per panel for mosaics; column-presence-validated, read-back verified. **Dry-run is supported but not a default** — `Execute(WriteBackPlan plan, bool apply)` takes `apply` as a required argument, so every caller states intent explicitly; the "default" belonged to the `--apply`-off CLI verbs, which retired with the consumer's console host 2026-06-11, to resurface as a TSM app action). `Reconcile/` answers goal-vs-actual (`Reconciler` + `CatalogStore.GetReconciliation`): TS goals (`exposure_plan.desired_count`) vs disk actuals (`inventory_filter`) per (target, filter), joined on the shared single-letter filter name — actuals are disk truth (TS's stale `acquired_count` is ignored). `ReconcilePolicy.Combined` (default) counts Light + Stars toward a goal; status is NotStarted/InProgress/Complete/Unplanned. Current consumer: TargetSchedulerManager (TP carries Catalog only transitively via NINA and uses none of it — see `CONSUMERS.md`); XFM / IS / ISP are planned, not yet consuming. Pure-managed → builds with `dotnet build`.
- **`Astronomy.Catalog.Tests`** — `net10.0-windows` x64, `OutputType=Exe`. xUnit tests for Astronomy.Catalog: the moved scanner tests (`Scan/`), schema creation (WAL, lookups), the `WriteCatalog` round-trip, the `TargetResolver` units (Both/Planned/Actual classification, name-mismatch, coordinate dedup, tolerance boundary, angular separation, out-of-range coercion), `CatalogBuilder` against a re-copyable BIRDWATCHER snapshot DB, and the `Reconciler` units (goal-vs-actual, Combined vs LightOnly, full-outer-join, over-shot-doesn't-mask-gaps), the write-back planners (`WriteBackPlanner` + surgical `SingleTargetPlanner` + the `TargetSchedulerWriter` round-trip + per-panel mosaic scan), and the TS-editing surface (`TsEditableSchema` field/bounds/enum pins, cadence-clear transactionality, editor refusals, effective-exposure resolution). 171 tests.
- `TargetSchedulerEditor.TrySetField(table, key, column, value) → (FieldEditResult?, RefusalReason)` is the guarded entry point: it folds the four open-db predicates (required columns / read-only / open sidecar / column present) into one structured-refusal call, plus a cadence guard — editing a target that has hand-authored override-order rows is refused (`RefusalReason.HasOverrideOrder`) rather than silently invalidating them. Consumers map `RefusalReason` to their own wording — the library names none.
- `TargetScheduler/TsEditableSchema` is the **declarative editable-field surface**: per-field `TsField` records (`Label`/`Type`/`Sentinel`+`SentinelLabel`/`Guarded` arm-before-edit/`Clears`) over the target/project/exposuretemplate tables, `TsFieldType` + `TsEnumValue` (`EnumValues`) so consumers render editors with zero UI-side schema, and `TsCadenceClear` (Target/Project/None) declaring which edits are cadence-breaking — `TrySetField` clears the affected `FilterCadenceItem` rows transactionally with the write. `TargetSchedulerEditor.ReadPlanEffectiveExposure` resolves a plan's exposure through its template via the standalone `EffectiveExposure` rule class (shared by catalog-side and raw-TS-side resolution).

## Astronomy.PCL / Astronomy.PCL.Native

- **`Astronomy.PCL.Native`** — vcxproj, x64-only C++ DLL. Statically links the vendored PixInsight Class Library (`Library\PCL\lib\x64\$(Configuration)\*-pxi.lib`). Public surface is the `extern "C"` C ABI in `include\Astronomy\PCL\XisfCApi.h`. Mirrors PCL's build flavor (`/MD`, `/fp:fast`, `stdcpp17`, `__PCL_WINDOWS`, `__PCL_AVX2`, `__PCL_FMA`) using the same MSVC toolset PCL itself uses (`v145` as of VS2026 — both wrapper and PCL bumped together); compiled with `AdvancedVectorExtensions2` (AVX2) — and since 2026-07-24 the **entire linked closure is too**: `PCL.vcxproj`, the six 3rd-party libs and `xisf.vcxproj` were restored to `AdvancedVectorExtensions2`, which is **upstream PCL's own configuration** (the zip's pristine vc16 projects: AVX2 + `__PCL_AVX2`). The local vc16→vc17/vc18 port had silently escalated the compiler flag to `AdvancedVectorExtensions512` while the `__PCL_AVX2` source macros stayed put, letting MSVC auto-emit ungated AVX-512 into the static libs (measured: 5,635 AVX-512 instructions in the Release wrapper DLL; zero after the restoration, verified by `dumpbin`). The floor matters because the portfolio's minimum target is the imaging machine's Ryzen 7 4800U — **Zen 2: AVX2 + FMA, no AVX-512** — where the escalated binaries would have died with an illegal-instruction fault the first time ISP touched the wrapper. Don't raise the flag again without raising the portfolio's hardware floor. The wrapper itself does no numerical work, but matching PCL's flags keeps any PCL header inlines instantiated in the wrapper TU bit-identical to the same inlines inside the static libs.
- **`Astronomy.PCL`** — `net10.0-windows` x64, `LangVersion latest`. Managed P/Invoke wrapper. Public surface: `XisfFile : IDisposable` (`Open` / `ImageCount` / `SelectImage` / `ReadImageF32()` returning a fresh array, plus the caller-allocated `ReadImageF32(float[] destination)` overload — prefer the latter in a loop), `XisfImageInfo`, `XisfColorSpace`, `XisfException`. ### PCL local build

`Library\PCL\` is the vendored Pleiades PixInsight Class Library, locally pruned to **Windows-only** — the macOS and Linux build trees were largely stripped (some Makefile stubs survive under `Library\PCL\src\modules\...`, but the actual source trees were removed). The canonical pinned snapshot is `Library\PCL\PCL-master.zip` (2025-02-22 per `archive/PCL-InterOp.md`). Re-extract on a fresh clone, or to discard local edits.

> **The build procedure** — re-extract, the four required env vars, building `PCL.sln`, and the
> test-data side effect — lives in `VERIFICATION.md` § *PCL native prerequisites*. What follows is the
> structure it operates on.

**Toolset.** **Every** vcxproj in the vendored tree is at `<PlatformToolset>v145</PlatformToolset>` — `PCL.vcxproj`, the six 3rd-party libs, `xisf.vcxproj`, *and* all ~38 file-format/process modules — matching `Astronomy.PCL.Native`. **Instruction set:** the 8 sln-visible projects (PCL + six 3rd-party + xisf) are at `AdvancedVectorExtensions2`, restored 2026-07-24 to upstream's own configuration after the local port had escalated them to AVX-512 (see § *Astronomy.PCL / Astronomy.PCL.Native* for why — the 4800U imaging machine has no AVX-512). The ~38 module projects were left at the escalated flag: their `.pxm`/`.dll` outputs are unused by this repo and run only inside PixInsight on this machine. The directory naming `vc17` under `src\3rdparty\*\windows\vc17\` and `src\modules\*\windows\vc17\` is historical PCL convention and was deliberately not renamed; only the main PCL solution moved from `src\pcl\windows\vc17\` → `src\pcl\windows\vc18\` to signal the VS2026 build flavor.

**Main solution.** `Library\PCL\src\pcl\windows\vc18\PCL.sln` carries **46 buildable vcxproj**: PCL, the six 3rd-party static libs and the xisf utility (the parts this repo consumes), plus six file-format modules and ~32 process modules that are built but unused here. Static libs land in `Library\PCL\lib\x64\{Debug,Release}\*-pxi.lib`, module and utility outputs in `Library\PCL\bin\x64\{Debug,Release}\` (~2.9 GB). `Astronomy.PCL.Native` consumes only the seven `.lib` outputs from `lib\x64\$(Configuration)\`.

**x64-only, tree-wide.** Every vendored PCL vcxproj declares only `Debug|x64` / `Release|x64` — this is not an xisf-specific local edit. Consequence: the `Debug|x86` / `Release|x86` → `Win32` mappings that `Astronomy.sln` carries for the eight PCL projects point at configurations that **exist in no project file**. They are dead entries (and unlike the x64 rows they carry a live `Build.0`), so selecting the x86 solution configuration fails rather than aliasing to something workable.

**xisf utility.** PCL's CLI test app at `Library\PCL\src\utils\xisf\`. Statically links the same seven `.libs` Astronomy.PCL.Native does (`PCL-pxi`, `lz4-pxi`, `zlib-pxi`, `zstd-pxi`, `lcms-pxi`, `cminpack-pxi`, `RFC6234-pxi`, plus `Userenv`). Built by PCL.sln (which lists xisf.vcxproj) or independently via `xisf.sln` in the same directory; both produce the same `xisf.exe`. (How to invoke it → `VERIFICATION.md`.)

**Re-snapshot caveat.** Re-extracting `PCL-master.zip` clobbers all local edits — the `vc18` directory, the v143→v145 toolset bumps, the Win32/x86 strip, anything else added under `Library\PCL\`. Note the toolset bump spans **~46 project files, not the eight** the tree's own solution highlights: re-applying to only PCL + 3rd-party + xisf leaves the modules on v143 and the solution broken. Plan to re-apply wholesale or keep a patch. **One local edit needs no re-apply:** the AVX2 instruction set — upstream's projects already carry `AdvancedVectorExtensions2`, so a fresh extract is born correct; just don't re-escalate it during the next toolset pass (that's how the AVX-512 drift happened the first time).

**Upstream Pleiades docs.** `Library\PCL\README.md` (PCL overview), `CODING_STYLE.md` (Pleiades C++ conventions), `COPYING.md` + `LICENSE.txt` (PCLL license) are unmodified upstream content; left alone deliberately so re-snapshot doesn't churn them.

### PCL interop

The hybrid architecture from `archive/PCL-InterOp.md` (the archived interop-rationale decision record) is **implemented** for the first surface (XISF read). Two projects:

- `Astronomy.PCL.Native` (C++ DLL, statically links PCL `.lib`s from `Library\PCL\lib\x64\`).
- `Astronomy.PCL` (managed P/Invoke wrapper, `net10.0-windows` x64).

C ABI is the source of truth: `Astronomy.PCL.Native\include\Astronomy\PCL\XisfCApi.h`. Every export is wrapped in `ASTRONOMY_PCL_TRY` / `ASTRONOMY_PCL_CATCH` (in `src\Exception.h`) — this catches `pcl::Exception` and `std::exception` and translates to status codes; the `catch (...)` branch picks up SEH (access violations etc.) due to `<ExceptionHandling>Async</ExceptionHandling>`. Last-error message is thread-local (`src\LastError.cpp`); consumers retrieve via `AstronomyXisf_GetLastErrorMessage` (two-call idiom: query length, alloc, fetch).

**Watch-out: don't use `XISFReader::ReadImage(FImage&)` for non-float source images.** PCL's auto-converting read path appears to need PixInsight platform services that aren't available in a host process — UInt16 or UInt32 sources surface as an unrecognized SEH exception ("Unknown C++ exception" at `catch (...)`). The wrapper dispatches on `ImageOptions.bitsPerSample` / `ieeefpSampleFormat`, reads in the file's native type (`UInt16Image`, `FImage`, `DImage`, …), then converts to float32 in our own loop. See `XisfCApi.cpp:AstronomyXisf_ReadImageF32`.

Adding new PCL surfaces: bind on demand. Add the `extern "C"` export to `XisfCApi.h` and `Astronomy.PCL.Native.def`, implement in `XisfCApi.cpp` wrapped in the macro, mirror the `[DllImport]` in `Astronomy.PCL/Interop/NativeMethods.cs`, expose the C# surface in `Astronomy.PCL`. Test in `Astronomy.Core.Tests/Tests/PCL/`.
